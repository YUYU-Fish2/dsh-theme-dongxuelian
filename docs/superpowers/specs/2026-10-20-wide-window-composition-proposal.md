执行更新：用户随后批准生成示意并要求开始；又明确要求重新生成图像、成品按该示意图，并指出聊天中间空白过大。原1280px共同构图首稿及“聊天只回归、不改图”的边界已被新指令替代。当前执行[P9计划](../plans/2026-10-20-wide-window-composition.md)与[P9-B任务](../../coordination/P9-B-task.md)：新图、1920px宽屏构图区、更宽输入/阅读区及聊天共同定位。用户还要求与DSH协同、只做正常使用必要检查。下文保留提案历史，不当作当前验收值。

## 观察与原因

- 用户提供的1265×817窗口中，输入区与抱书人物距离协调；2559×1395截图中，输入局促靠左、人物贴右，中间留白过大，图片矩形边界明显。这些是截图像素，不等于实测CSS视口。
- `client.js` 的空态输入宽度最多500px、左距最多48px；背景固定右偏移-190px、高度最多800px。二者分别依赖内容列左右边界，大窗口没有共同构图上限。
- 横向遮罩按整个内容容器的22%计算，未跟随图片实际边缘。宽屏时，图片开始的位置可能已经处于遮罩完全不透明区域，需要在复现中测量确认。
- P8既有矩阵只到1440px窗口，不能证明此次约2560px窗口效果合格。用户截图证明原生窗口已显示主题，但不代表全部桌面尺寸/DPI已验收。

## 方案选择

| 方案 | 效果与取舍 |
| --- | --- |
| 推荐：输入与人物使用居中的共同构图区 | 保留左输入右人物；超宽屏限制两者总跨度，把多余空间留在构图外侧，接近小窗口的关系。只需局部CSS适配。 |
| 图片铺满窗口 | 画面更满，但原图比例与宽屏不同，容易切脸、切书或人物过大，不优先采用。 |
| 输入整体居中、人物仍贴最右 | 改动较少，但两者关系仍随窗口宽度漂移，矩形纸片感也没有解决。 |

## 推荐设计

1. **保留已满意的小窗口。** 按会话内容列可用CSS宽度做容器查询，侧栏收放和打开分栏也参与适配；不按屏幕物理分辨率硬切档。现有窄列的阅读优先规则保留。
2. **为宽窗口建立共同构图区。** 初始试排宽度取1100–1280 CSS px，居中放在会话内容区；该范围为待预览参数。标题、输入与人物均相对此区域定位，超出后两者间距不再随整个窗口增长。优先复用官方容器和CSS变量，不移动消息DOM、不新增JS尺寸监听。
3. **调整比例而非全面放大。** 输入初始试排500–560 CSS px，保留正常字体和操作密度；图片等比显示，结合可用高度限制大小并向构图中心收拢。以人物脸、抱书与双手可见、输入不压住人物为标准。小窗口参数先保持，再确认过渡点。
4. **让图片边缘融合跟随图片范围。** 把承载图片的伪元素限制在共同构图对应的范围，纸白底继续铺满内容区；渐隐以图片实际显示边缘为参照，弱化矩形接缝。保留人物清晰度，不靠整体降低透明度遮掩边界；不修改原始图像文件。
5. **空态与聊天态分别验收。** 空态强调输入与人物的组合；聊天态保留可读正文宽度、不透明阅读面和代码内部横滚，右侧人物不能挤压消息或工具卡。此次截图仅证实空态问题，聊天态属于防回归检查，不预设也需要相同幅度的调整。
